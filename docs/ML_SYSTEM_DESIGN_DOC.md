# ML System Design Doc — AI‑модерация Squads (CARCASE ARENA)

Этот документ — главный артефакт модуля: **бизнес‑контекст → DS/ML формулирование → пилотирование**.
Сервис может использовать внешнюю LLM (OpenAI). Тогда “ML‑артефакты” = policy + prompt + пороги + данные оценок + мониторинг качества.

Связанные документы:
- Интеграция в продукт: `docs/INTEGRATION.md`
- Хранение и аудит: `docs/DATA_MODEL.md`

## 1) Бизнес‑контекст

### 1.1 Продукт и точка применения
- Продукт: CARCASE (Telegram‑бот) + CARCASE ARENA (Telegram Mini App).
- UGC: `squad name`, `squad description`.
- Моменты модерации: создание сквада, редактирование описания (и админ‑правки).

### 1.2 Проблема
UGC может содержать: токсичность/оскорбления, hate/extremism, сексуальный контент, призывы к насилию/суициду, рекламу/скам, персональные данные.

### 1.3 Бизнес‑цель и ожидаемый эффект
Цель: снизить долю запрещённого UGC, попадающего в продукт, при контролируемом влиянии на UX/конверсию.

### 1.4 Стейкхолдеры
- Owner (ключевой заказчик): владелец продукта CARCASE (в рамках учебного проекта — автор/владелец продукта).
- Ops/Support: модератор/саппорт (Global Admin) + правила реагирования на алерты.
- Разработка: Mini App backend + moderation-service + batch/monitoring.

### 1.5 Скоуп / не‑скоуп
В скоупе:
- модерация текста squad name/description.

Вне скоупа (MVP):
- чаты, никнеймы, картинки, вложения.
- генерация контента (мы не “переписываем” тексты автоматически, только принимаем решение и (опц.) даём краткую причину).

### 1.6 Ограничения продукта (MVP)
- Поддерживаемые языки: RU/EN (остальные — best effort через LLM).
- `squad name`: короткое (в продукте уже есть ограничения по длине и разрешённым символам).
- `squad description`: до ~160 символов (MVP).
- Создание сквада стоит `5000 Scrap` (платёж относится к бизнес‑логике продукта; модерация не должна приводить к несправедливому списанию из‑за FP).

### 1.7 Метрики (business + guardrails)
Business:
- доля репортов/жалоб на squads UGC
- доля запрещённого UGC, дошедшего до публикации (по ручной выборке)
- доля ручных модераций

Guardrails:
- конверсия “создать сквад”
- p95 latency на create/update
- error rate
- стоимость на 1k модераций (LLM calls / tokens)

### 1.8 Нефункциональные требования (черновик)
- Доступность сервиса модерации: 99%+ (учебный стенд).
- Таймаут модерации: строгий (например, 1–2 секунды). Если таймаут/ошибка провайдера — не “ломаем продукт” (см. fallback ниже).
- Безопасность: секреты только через env/secret storage; никаких ключей в репозитории.

### 1.9 Риски
- FP: блокируем нормальный текст → падение UX/конверсии.
- FN: пропускаем нарушения → репутация/санкции.
- Дрейф внешней модели (изменение поведения провайдера).
- Рост стоимости при нагрузке/абьюзе.

## 2) DS/ML формулирование

### 2.0 Тип задачи
Policy‑based модерация как multi‑label классификация + оркестрация решения:
`categories[]` → `decision allow/block/review`.

### 2.1 Сущности и решения
Вход:
- `text`, `field` (name/description), `action` (create/update), контекст (user_id, squad_id).

Выход:
- `decision`: `allow | block | review`
- `categories`: список категорий нарушений
- `reason_short`: короткое объяснение (для логов/админа)
- `policy_version`, `prompt_version`, `model`

### 2.2 Policy (категории)
Минимальный набор категорий:
- `profanity_insult_harassment`
- `hate_extremism_terror`
- `sexual`
- `self_harm`
- `violence`
- `spam_ads_scam`
- `pii`

Правила маппинга (MVP, реализуемо):
- Жёсткий `block`:
  - `hate_extremism_terror` (в т.ч. символика/призывы)
  - `sexual` при явном контенте (отдельный флаг “minors” — всегда block, если добавим в policy)
  - `self_harm` при прямых призывах/инструкциях
  - `spam_ads_scam` при явной рекламе/скаме/контактах для рекламы
- `review` (ручная очередь):
  - пограничные случаи по любым категориям
  - `pii` (часто лучше дать человеку решить, особенно если это не злонамеренно)
- `allow`: остальное

### 2.3 Решение по `review` и списанию Scrap (принятое решение)
- `review` = **pending + админ‑очередь** (human-in-the-loop), чтобы:
  - снижать риски FP/FN,
  - собирать human truth для качества внешней LLM.
- Scrap за создание сквада списываем:
  - сразу при `allow`,
  - **только после approve** при `review` (если к моменту аппрува Scrap недостаточно — автоматический reject).

### 2.4 Подход к “модели” (LLM)
- Провайдер: OpenAI API.
- “ML‑артефакты”: `policy_version`, `prompt_version`, пороги/правила маппинга.
- Требования к ответу LLM: строго JSON по схеме (валидируем), temperature=0 (максимально детерминированно), короткий `reason_short`.

### 2.5 Предобработка и защита от обходов (MVP)
- Нормализация текста: lower, trim, схлопывание пробелов, удаление “декоративных” символов.
- Детектор обфускации (очень простой): удаление неалфанумерика и повторная проверка (как сейчас в blacklist, но расширяем для LLM).
- Rate limiting по user_id (на стороне продукта уже есть ограничения; добавляем/дублируем на сервисе модерации).
- Кэширование решения по `hash(text_norm, field, policy_version, prompt_version)` (TTL, например 7 дней) для снижения стоимости.

### 2.6 Данные и “истина”
Источники:
- онлайн события модерации (решение LLM + контекст)
- ручные решения Global Admin (approve/reject/edit)
- апелляции/репорты (если появятся)

Golden set:
- периодически собираемый сэмпл (стратификация по decision/category)
- ручная разметка (human truth) для offline метрик

### 2.7 Оценка качества
Offline (golden set):
- precision/recall/F1 для `block`
- доля `review` (нагрузка на модерацию)

Online:
- доля override (админ отменил решение)
- тренд по доле `block/review`
- консистентность решений на повторных запросах (по одинаковому тексту)

## 3) Пилотирование

### 3.1 Стратегия
Staged rollout (feature flag) на `/api/squads/*`:
- 0% → 10% → 50% → 100%
- стабильный сплит по `user_id`

### 3.2 План пилота (что сравниваем)
- Период baseline: 7 дней до включения (если данных нет — начинаем собирать сразу, пилот после накопления).
- Вариант пилота: staged rollout (процент трафика) + ручная оценка сэмплов.
- Сегменты: create vs update, RU vs non‑RU, new users vs returning.

### 3.3 Критерии успеха (черновые, уточняются после baseline)
Success:
- снижение жалоб/нарушений
- приемлемая доля FP (по апелляциям/override и ручной выборке)

Guardrails:
- конверсия в создание/редактирование не падает > 1–3% (абсолютно) — уточнить после baseline
- p95 latency и error rate в пределах SLA (см. 1.8)
- стоимость в пределах бюджета (первый ориентир задаём в деньгах/сутки)

### 3.4 Откат (rollback)
Условия остановки:
- скачок FP/override
- рост ошибок/таймаутов
- деградация конверсии

## 4) Продуктовые UX‑решения (MVP)
- `review` на create: пользователь видит статус “на проверке” (без публикации).
- `review` на update: старое описание остаётся, новый текст уходит на проверку.
- `block`: нейтральное сообщение “текст не проходит правила, попробуйте изменить”.
