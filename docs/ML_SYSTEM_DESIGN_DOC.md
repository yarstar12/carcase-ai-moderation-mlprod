# ML System Design Doc — AI‑модерация Squads (CARCASE ARENA)

Этот документ — главный артефакт модуля: **бизнес‑контекст → DS/ML формулирование → пилотирование**.
Сервис может использовать внешнюю LLM (OpenAI). Тогда “ML‑артефакты” = policy + prompt + пороги + данные оценок + мониторинг качества.

## 1) Бизнес‑контекст

### 1.1 Продукт и точка применения
- Продукт: CARCASE (Telegram‑бот) + CARCASE ARENA (Telegram Mini App).
- UGC: `squad name`, `squad description`.
- Моменты модерации: создание сквада, редактирование описания (и админ‑правки).

### 1.2 Проблема
UGC может содержать: токсичность/оскорбления, hate/extremism, сексуальный контент, призывы к насилию/суициду, рекламу/скам, персональные данные.

### 1.3 Бизнес‑цель и ожидаемый эффект
Цель: снизить долю запрещённого UGC, попадающего в продукт, при контролируемом влиянии на UX/конверсию.

### 1.4 Стейкхолдеры
- Owner (ключевой заказчик): (заполнить)
- Ops/Support: (заполнить)
- Разработка: (заполнить)

### 1.5 Скоуп / не‑скоуп
В скоупе:
- модерация текста squad name/description.

Вне скоупа (MVP):
- чаты, никнеймы, картинки, вложения.

### 1.6 Метрики (business + guardrails)
Business:
- доля репортов/жалоб на squads UGC
- доля запрещённого UGC, дошедшего до публикации (по ручной выборке)
- доля ручных модераций

Guardrails:
- конверсия “создать сквад”
- p95 latency на create/update
- error rate
- стоимость на 1k модераций (LLM calls / tokens)

### 1.7 Риски
- FP: блокируем нормальный текст → падение UX/конверсии.
- FN: пропускаем нарушения → репутация/санкции.
- Дрейф внешней модели (изменение поведения провайдера).
- Рост стоимости при нагрузке/абьюзе.

## 2) DS/ML формулирование

### 2.1 Сущности и решения
Вход:
- `text`, `field` (name/description), `action` (create/update), контекст (user_id, squad_id).

Выход:
- `decision`: `allow | block | review`
- `categories`: список категорий нарушений
- `reason_short`: короткое объяснение (для логов/админа)
- `policy_version`, `prompt_version`, `model`

### 2.2 Policy (категории)
Минимальный набор категорий:
- `profanity_insult_harassment`
- `hate_extremism_terror`
- `sexual`
- `self_harm`
- `violence`
- `spam_ads_scam`
- `pii`

Правила маппинга (черновик):
- `hate_extremism_terror` → block
- явный `spam_ads_scam` → block, пограничный → review
- `pii` → чаще review
- остальное: явное → block, пограничное → review

### 2.3 Данные и “истина”
Источники:
- онлайн события модерации (решение LLM + контекст)
- ручные решения Global Admin (approve/reject/edit)
- апелляции/репорты (если появятся)

Golden set:
- периодически собираемый сэмпл (стратификация по decision/category)
- ручная разметка (human truth) для offline метрик

### 2.4 Оценка качества
Offline (golden set):
- precision/recall/F1 для `block`
- доля `review` (нагрузка на модерацию)

Online:
- доля override (админ отменил решение)
- тренд по доле `block/review`
- консистентность решений на повторных запросах (по одинаковому тексту)

## 3) Пилотирование

### 3.1 Стратегия
Staged rollout (feature flag) на `/api/squads/*`:
- 0% → 10% → 50% → 100%
- стабильный сплит по `user_id`

### 3.2 Критерии успеха
Success:
- снижение жалоб/нарушений
- приемлемая доля FP (по апелляциям/override и ручной выборке)

Guardrails:
- конверсия в создание/редактирование не падает > X%
- p95 latency и error rate в пределах SLA
- стоимость в пределах бюджета

### 3.3 Откат (rollback)
Условия остановки:
- скачок FP/override
- рост ошибок/таймаутов
- деградация конверсии
