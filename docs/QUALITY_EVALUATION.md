# Quality evaluation (validation dataset) — approach

Цель: иметь воспроизводимую и регулярно исполняемую проверку качества внешней LLM‑модерации, независимую от текущего трафика и скорости накопления human truth.

Важно: validation dataset не участвует в обработке пользовательских запросов. Он используется только в оффлайн‑контуре оценки качества.

## 1) Что такое validation dataset

Validation dataset (также “golden set”) — это фиксированный набор примеров “текст → ожидаемый результат” для регулярной проверки качества:
- быстрый регрессионный тест при изменениях `policy/prompt/model`;
- мониторинг деградаций/дрейфа поведения внешнего провайдера;
- воспроизводимое доказательство качества на одинаковом наборе.

Никакая “вторая модель” для сравнения не нужна. Оценку делает детерминированный скрипт: он берёт пример, получает предсказание от нашей системы и сравнивает его с ожидаемым ответом.

## 2) Источники и состав набора

Validation dataset v1 формируется как смесь:
1) **Синтетические примеры** по шаблонам, покрывающие все ключевые категории policy, включая варианты обфускации и смешанных языков.
2) **Кураторские примеры** из ручной очереди `review` (human truth) после анонимизации и удаления потенциальных PII.

Рекомендации по составу:
- общий объём “full” набора: 5k–20k примеров (достаточно для стабильных метрик);
- отдельный “smoke/regression” поднабор: 200–500 примеров (быстро и дёшево гонять часто);
- стратификация: в full‑наборе должны быть сотни примеров на каждую критичную категорию и большой пул “чистых” текстов (expected=`allow`), плюс небольшой набор “hard cases”.

## 3) Формат (пример схемы JSONL)

Каждая строка — один пример:
- `id`: строковый идентификатор
- `dataset_version`: например `v1`
- `field`: `squad_name | squad_description`
- `action`: `create | update`
- `text`: строка
- `expected_categories`: список категорий (может быть пустым)
- `expected_decision`: `allow | block | review` (опционально, можно вычислять маппингом policy)
- `source`: `synthetic | review_human_truth | other`
- `notes`: опционально

## 4) Как считается качество (оффлайн evaluation job)

Evaluation job выполняет:
1) загрузку датасета из S3/MinIO по `dataset_version`;
2) прогон примеров через **тот же** пайплайн модерации, что используется в проде (`rules → LLM → decision`);
3) сравнение `predicted_*` vs `expected_*`;
4) расчёт метрик и сохранение отчёта.

Результат evaluation:
- отчёт сохраняется в S3/MinIO;
- агрегаты (по необходимости) пушатся в Prometheus через Pushgateway и визуализируются в Grafana.

## 5) Метрики (минимальный набор)

Decision‑уровень:
- `precision_block`, `recall_block`, `f1_block` (на validation set)
- `review_rate`, `block_rate`, `allow_rate`
- “критичный FN”: доля случаев, где `expected_decision=block`, но `predicted_decision=allow`

Category‑уровень (по ключевым категориям policy):
- precision/recall по каждой категории (multi‑label)

Отдельно (из прод‑данных) считаем метрики по human truth, когда контур `review` начнёт давать достаточную разметку.

## 6) Стоимость и ограничения (чтобы не “сжечь бюджет”)

Validation evaluation не обязан прогонять full‑набор каждый день.

Рекомендуемая стратегия:
- **часто** (daily или on‑change): smoke‑набор 200–500 примеров;
- **редко** (weekly или manual): full‑набор 5k–20k примеров.

Контроль затрат:
- hard cap на число примеров в одном запуске;
- rate limit и/или параллелизм не выше заданного;
- алерты по бюджету (например при приближении к дневному лимиту запросов/токенов).

## 7) Версионирование и воспроизводимость

Для воспроизводимости любой оценки в отчёт должны попадать:
- `dataset_version`
- `policy_version`, `prompt_version`
- `model` (и при необходимости `base_url/provider`)
- время запуска и параметры (smoke/full, лимиты)
